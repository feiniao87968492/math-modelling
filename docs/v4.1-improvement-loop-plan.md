# v4.1 Plan — Improvement Loop on Rule-Constrained Workflow

## 背景

v4 解决了"流程是否合规"的问题：通过 Markdown-first 审计、强阻断确认、readiness gate、rollback 与 fixed-point review，把数学建模从机械 YAML 状态机变成规则约束下的协作。

但实际比赛和复盘中暴露出一个新缺口：v4 的 9 个 reviewer 全部是**一致性把关人**。它们问的都是"现在这个东西够不够格"，没人在问"这个东西能不能更好"。具体表现：

- Stage 6 通过后，metrics 直接进入 claim-registry，没有 baseline 冻结快照；
- Stage 6→7→8→9→10 是一次过的瀑布，rollback 只在"发现 1-5 阶段缺陷"时触发，从来不是因为"我们其实可以更好"；
- claim level 只升不降的方向缺失，从 `feasible_baseline` 到 `validated_optimum` 之间没有"可量化升级路径"的记录；
- 没有"已尝试 / 未尝试 / 已放弃"的 frontier，下一轮容易重复尝试或自欺。

一句话：v4 是单向防御，不是双向迭代。

## v4.1 目标

在保留 v4 全部硬护栏的前提下，新增一个 **improvement loop**：让主 agent 在已生成模型的基础上，主动发现不足并按规则推进下一轮优化。

### 必须保留

- 所有 v4 强阻断规则；
- fixed review points 与 reviewer invocation template；
- readiness gate / rollback / final evidence gate；
- claim grounding；
- "用户沉默不等于确认"。

### 必须新增

- baseline 冻结机制（防主观比较）；
- 攻守两个 improvement reviewer（防自欺）；
- improvement frontier（防重复试同一方向）；
- improvement decision（防静默升级 claim level）；
- 收敛条件（防无限循环）。

## 架构

复用 v4 三层结构，不引入第四层：

```
Layer 1  Rule Layer            ── 11 + 4 = 15 条强阻断规则
Layer 2  Autonomous Execution  ── 主 agent 在规则边界内自主推进，新增 improve 命令切片
Layer 3  Snapshot Layer        ── workflow.md / decisions / gates / branches /
                                  rollbacks / claims / reviews / improvements
```

新增的 `improvements/` 目录与现有审计目录对等，不是子级。

## 新增 Reviewer 角色

参考 `math-olympiad` skill 的对抗 verifier 思路，攻守配对使用。

### Improvement-Critique Reviewer（攻方，红队视角）

Trigger：在 Stage 6 PASS 且 baseline 已 freeze 后，由主 agent 通过 `/math-modeling improve` 调度。

Review focus：
- 对照 baseline-snapshot 与 sensitivity 报告，挑出可以更好的方向；
- 每条建议必须给出 hypothesis、量化收益假设（before vs after 的预期 metric 与置信区间）、实现难度估计、是否需要新数据/求解器、是否触发 fallback / rollback、是否会改变 claim level；
- 拒绝模糊 claim（"应该会更好"、"鲁棒性更强"）。

Forbidden behavior：
- 不得 confirm 用户决策；
- 不得 clear blocker；
- 不得 mark improvement round complete；
- 不得跨过 Skepticism Reviewer 直接驱动主 agent 实现。

### Improvement-Skepticism Reviewer（守方）

Trigger：紧随 Improvement-Critique 之后，由主 agent 在同一个 improvement round 内调度。

Review focus：
- 质疑攻方提议是否破坏 baseline、是否变相 cherry-pick；
- 检查 hypothesis 是否假设比当前更强、是否真能跑出预期收益；
- 对照 frontier，标记重复尝试或与已放弃方向冲突的提议；
- 评估提议是否会拉低当前 claim level 而不自知。

Forbidden behavior：
- 与 v4 reviewer global boundary 一致；
- 不得直接否决一条提议而不给证据 reference；
- 不得在没有 Critique 输出的情况下单独运行。

### 在 protocol-subagent-delegation.md Risk-Triggered Reviewers 表里追加

| Risk | Reviewer |
|---|---|
| improvement opportunity proposed | Improvement-Critique Reviewer |
| improvement proposal needs adversarial check | Improvement-Skepticism Reviewer |

## 新增 Markdown 审计目录

### `improvements/` 目录布局

```
improvements/
├── improvement-log.md           总目录，列出所有轮次摘要
├── improvement-frontier.md      已尝试 / 进行中 / 未尝试 / 已放弃
└── round-N.md                   每一轮的完整记录
```

### `improvement-log.md` 模板

```markdown
# Improvement Log

| Round | Status | Started | Closed | Method change | Decision link |
|---|---|---|---|---|---|
| 0 | baseline | YYYY-MM-DD | - | (frozen baseline) | - |
| 1 | implemented | YYYY-MM-DD | YYYY-MM-DD | LGBM + lag features | decisions/decision-improvement-round-1.md |
| 2 | rejected | YYYY-MM-DD | YYYY-MM-DD | scenario tree extension | decisions/decision-improvement-round-2.md |
```

### `improvement-frontier.md` 模板

```markdown
# Improvement Frontier

## Tried and kept
- LGBM + lag features (round 1)

## Tried and reverted
- (none yet)

## Proposed but not yet attempted
- piecewise linearization of Q3 device cost
- second-stage stochastic recourse for Γ-scenarios

## Abandoned
- end-to-end neural surrogate (无 GPU 资源, decision-improvement-round-2.md)
```

主 agent 在每一轮 Critique 调度前，**必须先读 frontier**，并把 frontier 路径写入 reviewer invocation template 的 Required Reads。

### `round-N.md` Required Sections

```markdown
## Round metadata
## Baseline reference
## Critique findings
## Skepticism findings
## Synthesized proposal
## Risk assessment
## Required readiness or rollback
## Claim level delta
## User decision link
## Implementation summary
## Before vs after metrics
## Frontier update
```

最后三段允许在用户 confirm 并完成实现后追加，不要求一次性写完。

## 新增 baseline-snapshot 强制冻结

### `claims/baseline-snapshot.md`

Stage 6 第一次 PASS 时由主 agent 强制写入。改造后 Stage 6 的 Done When 列表追加：

- baseline-snapshot.md exists and lists frozen primary metrics

### 模板

```markdown
# Baseline Snapshot

## Frozen at
- Stage: 6
- Date: YYYY-MM-DD
- Validation review: reviews/stage6-validation-review.md

## Primary metrics
| Metric | Value | Source artifact |
|---|---|---|
| WAPE | 0.288 | data/validation/validation-report.md |
| Q2 obj | 9,016,061 | data/results/q2-solution.csv |
| Q3 obj | 9,893,432 | data/results/q3-solution.csv |

## Claim level
- feasible_baseline (or whichever Stage 6 closed at)

## Reproducibility anchor
- code commit: <sha>
- input dataset hash: <hash>
- solver version: <ver>
```

每轮 improvement 必须以这份 snapshot 为参照，不允许"和上一轮比"或"比之前感觉更好"。

## 新增命令 `/math-modeling improve`

### 入口语义

```
/math-modeling improve            进入下一轮 improvement，自动选择 round 编号
/math-modeling improve round N    显式指定 round 编号
/math-modeling improve status     输出 frontier + log 摘要
/math-modeling improve close      关闭当前 round，写 before-vs-after 与 frontier 更新
```

自然语言触发："还能更好吗"、"优化这个模型"、"做下一轮"、"reduce WAPE 再试一次"。

### 默认运行前置条件

主 agent 必须先校验：

1. `gates/stage6-*` 存在且为 PASS 或 PASS_WITH_WARNINGS；
2. `claims/baseline-snapshot.md` 存在；
3. Stage 7 sensitivity 已写入（若 sensitivity 未做，回到 v4 既有流程，先完成 Stage 7）；
4. 没有 pending decision；
5. 当前 round-N.md 未处于 in_progress 状态。

任一不满足，主 agent 输出阻断说明，不进入 Critique 调度。

### 推进流程

```
1. 读 improvement-frontier.md 与 baseline-snapshot.md
2. emit reviewer invocation template, spawn Improvement-Critique
3. emit reviewer invocation template, spawn Improvement-Skepticism
   (Required Reads 必含上一步 Critique 输出)
4. 主 agent 综合 Critique + Skepticism, 写 round-N.md 前 6 段
5. 主 agent 写 decisions/decision-improvement-round-N.md, 标记 PENDING
6. 阻断, 等用户 confirm
7. confirm 后:
     - 若改动触发已确认方法/模型结构变化, 走 v4 fallback + rollback 流程
     - 否则按 Stage 5/6 既有合同重做相关切片
8. 实现完成, 写 round-N.md 后 3 段 + 更新 frontier + 更新 log
9. 重新跑 Stage 6 validation review, 复用 v4 reviewer invocation template
10. /math-modeling improve close 收尾
```

第 7 步是关键 — improvement loop **复用** v4 的 fallback / rollback / decision / gate / readiness 机制，不自建一套。

## 新增强阻断规则

追加到 SKILL.md §强阻断规则 第 12-15 条：

```
12. improvement round 必须以 baseline-snapshot.md 为对照, 禁止主观比较或与上一轮比较。
13. improvement 提议必须经过 Improvement-Critique 与 Improvement-Skepticism 双 reviewer,
    且经用户 confirm, 方可进入实现。
14. 改动若覆盖已确认方法/模型结构/证据路径, 按 v4 既有 fallback 与 rollback 规则处理,
    不得绕开。
15. improvement round 不得静默升级 claim level; 升级必须由对应 readiness/evidence gate
    重新评估通过。
```

第 14 条让 improvement loop 不会成为绕过 v4 护栏的后门。

## 收敛条件

`/math-modeling improve` 默认在以下任一条件时停止追加新 round：

1. 用户主动 stop；
2. 边际收益小于用户在 round-1 元数据里设的阈值（`metadata: marginal_threshold`）；
3. 当前 claim level 已达到目标 ceiling（在 round-1 元数据里声明的 `target_claim_level`）；
4. 连续 K 轮（默认 K=2）Skepticism Reviewer 给出 BLOCKING risk 且无法被 Critique 反驳；
5. 资源约束触发（用户在 frontier 里标记的 abandoned 方向已覆盖剩余高潜力方向）。

主 agent 默认不主动开新 round，每一轮都需要用户 confirm，与 v4 强阻断原则一致。

## Regression 新增检查项

在 `regression/` 加 4 条最小可执行 fixture：

1. `improvement-baseline-required.md` — Stage 6 PASS 后未生成 baseline-snapshot.md, 期望 `/math-modeling improve` 阻断；
2. `improvement-double-reviewer.md` — 缺少 Skepticism review artifact, 期望 round-N.md 不得写 Synthesized proposal 段；
3. `improvement-frontier-no-duplicate.md` — Critique 提议命中 frontier "Tried and kept" 项, 期望 Skepticism BLOCKING；
4. `improvement-claim-level-no-silent-upgrade.md` — round-N.md 写入更高 claim level 但未触发 readiness gate, 期望主 agent 阻断并要求新 gate。

测试夹具沿用 v4 regression 的 markdown fixture 风格，不引入新框架。

## 与 v4 兼容性

v4.1 不破坏任何 v4 行为：

- 没有 baseline-snapshot 时, `/math-modeling improve` 不可用, 主流程完全等同 v4；
- 不调用 improve 命令的项目, v4.1 与 v4 行为完全相同；
- improvement reviewer 是 Risk-Triggered, 不进入 fixed review point, 不影响 v4 的 4 个硬 gate。

## 风险

### 风险 1：improvement 收益虚高

Critique 可能给出乐观估计，实际跑出来不及预期。

缓解：round-N.md 必须写 before vs after 实测 metric, frontier 标记 reverted, log 永久保留。

### 风险 2：用户被动 confirm 形成 rubber stamp

每一轮都阻断 confirm 容易让用户疲劳。

缓解：decision-improvement-round-N.md 模板必须包含"Skepticism BLOCKING risks"专段, 把守方的反驳前置, 不能藏在 review markdown 深处。

### 风险 3：与 v4 fallback 协议混淆

improvement 改动若触发 method 或 structural revision, 容易被当成 improvement 而绕过 rollback。

缓解：强阻断规则第 14 条 + protocol-improvement-loop.md 明确写 "若 round-N 改动落入 method/structural revision, 必须先生成 rollback 文档, 再进入 round-N 实现段"。
