# v4.2 Plan — Improvement Hardening + Competition Realism

## 背景

v4.1 把"已生成模型如何按规则迭代变好"这个缺口补上了：baseline 冻结、攻守双 reviewer、improvement frontier、四条新强阻断规则、双 reviewer 风险触发、`/math-modeling improve` 命令族。从协议层看，单向防御变成了双向迭代。

但 v4.1 自己也留下五个能直接点名的缺口：

- `/math-modeling improve` 只有 markdown fixture 级回归，没有像 readiness gate / export / rollback 那样的 command-flow harness，**协议是否真被执行**仍靠主 agent 自觉；
- 9 个 reviewer 的输出契约是自然语言 review focus + forbidden behavior，缺结构化 schema；reviewer 漂移、rubber stamp、漏检不会被自动捕获；
- `claims/baseline-snapshot.md` 是单一 metric 表，但实际竞赛多问联动且各有主指标，Q3 改进很容易撞掉 Q1 baseline 而无人察觉；
- 时间预算完全是隐变量，比赛硬截止下没有任何 stage-level burn-down；超时只能事后复盘；
- Stage 10 的论文素材 grounding 仍靠人工对：每个数字 / 公式 / 图是否能在 `claim-registry.md` 找到 entry，没有 export-time scanner，是 v4.1 没盖到的最后一道 hallucination 漏洞。

一句话：v4.1 把流程跑通了，v4.2 要让流程**自检**并对齐**真实比赛约束**。

## v4.2 目标

在保留 v4 + v4.1 全部硬护栏的前提下，做两件事：**hardening**（让 v4.1 协议被自动验证）和 **competition realism**（让流程对齐真实赛场的时间与论文证据约束）。

### 必须保留

- v4 全部 11 条强阻断规则与 4 个 fixed review points；
- v4.1 全部 4 条强阻断规则（baseline 对照、双 reviewer 必经、改动覆盖已确认方法走 fallback+rollback、claim level 不得静默升级）；
- readiness gate / rollback / fallback / Final Evidence Gate / human-confirmation / memory-update 的边界与 ownership；
- "用户沉默不等于确认"；
- improvement loop 复用既有协议、不自建并行状态机的根原则。

### 必须新增

- improve 命令级 harness（防协议口惠而实不至）；
- reviewer 输出结构化 schema + reviewer-eval regression（防漂移与 rubber stamp）；
- per-question baseline 与 per-question frontier（防多问联动下的 baseline 互撞）；
- stage-level 时间预算与 burn-down（防硬截止隐变量）；
- export-time paper grounding scanner（防论文里出现 claim-registry 找不到的数字 / 公式 / 图）。

## 架构

继续复用 v4 三层结构，**不引入第四层**：

```
Layer 1  Rule Layer            ── 11 + 4 + 5 = 20 条强阻断规则
Layer 2  Autonomous Execution  ── 主 agent 在规则边界内自主推进
                                  新增 time-budget 切片与 paper-grounding scanner 切片
Layer 3  Snapshot Layer        ── workflow.md / decisions / gates / branches /
                                  rollbacks / claims / reviews / improvements
                                  新增 schemas/ 与 time-budget.md 两个对等审计入口
```

新增的 `schemas/` 与 `time-budget.md` 与现有审计目录对等，不挂在 improvements/ 或 reviews/ 之下。

### 工作项 1 — improve 命令级 harness

#### 为什么需要

v4.1 在 `regression/` 落地了 4 条 markdown fixture（baseline-required / double-reviewer / frontier-no-duplicate / claim-level-no-silent-upgrade），但这些是**静态 markdown 契约**，不是命令级行为校验。其它命令（readiness gate / export / rollback）都已有 command-flow harness（`command_readiness_gate_flow.py`、`command_export_flow.py`、`command_rollback_flow.py`）+ 对应 `test_*_command_flow.py` 一一对应。`/math-modeling improve` 没有 harness 意味着：

- 入口前置条件是否真按 `protocol-improvement-loop.md` Preconditions 校验，无法自动验证；
- 双 reviewer 的调度顺序（Critique 必须先于 Skepticism、Skepticism 的 Required Reads 必须包含 Critique 输出）依靠主 agent 自觉；
- round-N.md 段落顺序约束（前 6 段在 confirm 前、后 3 段在 implementation 后）依靠主 agent 自觉；
- frontier 在 round close 时是否正确更新，没有自动检查。

#### 新增 / 改动

```
regression/command_improve_flow.py                           新增 harness
regression/test_improve_command_flow.py                      新增 pytest
regression/improve-flow-fixtures/                            新增最小 fixture 集
  ├── precondition-baseline-missing/
  ├── precondition-stage7-missing/
  ├── precondition-pending-decision/
  ├── precondition-round-in-progress/
  ├── reviewer-order-skepticism-before-critique/
  ├── round-section-order-synthesized-before-skepticism/
  ├── round-close-frontier-not-updated/
  └── happy-path-single-round/
```

harness 沿用既有 deterministic simulation 风格（参考 `command_readiness_gate_flow.py`），不引入新框架。每个 fixture 是一个最小项目目录，harness 模拟 `/math-modeling improve` 的命令调度，断言期望的 blocker / artifact / claim level 行为。

#### 回归保障

- happy-path-single-round：模拟一轮完整 improve（baseline → critique → skepticism → round-N 前 6 段 → decision PENDING → confirm → implementation → round-N 后 3 段 → frontier 更新 → close），全部自动通过；
- 每个 precondition fixture：harness 期望命令在对应步骤阻断且写出符合 `protocol-improvement-loop.md` 的 blocker 说明；
- reviewer-order / round-section-order 两条：harness 期望命令在违反顺序时立即阻断，不允许下一步动作。

预期 `pytest -x -q` 总数从 32 升到约 40。

### 工作项 2 — Reviewer 输出 schema + reviewer-eval regression

#### 为什么需要

v4.1 plan 风险段已经写明「**Critique 可能给出乐观估计** / **每一轮都阻断 confirm 容易让用户疲劳形成 rubber stamp**」。当前缓解只有"前置 Skepticism BLOCKING risks 到 decision 文档"一条，且只是约定，没有自动检查。具体盲点：

- 9 个 reviewer profile（Stage 4/5/6/10 + 5 个 risk-triggered 含两个 improvement reviewer + grounding/specialists/validation-paper）的输出 markdown 没有强制 schema，章节标题、findings 粒度、confidence 表达全凭 reviewer 自觉；
- reviewer 漂移无法被 fixture 捕捉：把同一份 buggy artifact 喂给 reviewer，是否能稳定 flag 出问题，没有 ground-truth 数据；
- reviewer 自己的 forbidden behavior（如"不得 confirm 用户决策""不得 clear blocker"）违规时，dispatcher 无法自动识别。

#### 新增 / 改动

```
schemas/                                                     新增审计目录
  ├── reviewer-output-schema.md                              结构化输出契约
  └── reviewer-self-discipline-checklist.md                  forbidden behavior 自检清单

references/protocol-subagent-delegation.md                   追加 schema 引用
SKILL.md §强阻断规则                                          追加第 16 条

regression/reviewer-eval/                                    新增评测目录
  ├── ground-truth/
  │   ├── stage4-buggy-method-selection.md
  │   ├── stage5-buggy-implementation-mismatch.md
  │   ├── stage6-buggy-validation-claim.md
  │   ├── stage10-buggy-paper-grounding.md
  │   ├── improvement-buggy-cherry-pick.md
  │   └── improvement-buggy-frontier-duplicate.md
  ├── expected-flags/
  │   └── <reviewer-id>__<fixture-id>.md
  └── test_reviewer_outputs.py
```

`reviewer-output-schema.md` 至少强制：

- `## Findings` 每条 finding 必须含 `Type` / `Severity (BLOCKING/WARNING/INFO)` / `Evidence reference (file:line or section)` / `Recommended action`；
- `## Required reads referenced` 列出本次评审实际用到的 artifact 路径；
- `## Confidence` 必须给出 `high / medium / low` + 一句 rationale；
- `## Forbidden-behavior self-check` 显式声明本次评审没有越界（与 `reviewer-self-discipline-checklist.md` 对齐）。

`test_reviewer_outputs.py`：把 ground-truth fixture 提供给 reviewer，断言期望 flag 集合是 reviewer 实际输出 flag 的子集（漏检失败、误检 warning 不算失败但记录）。

#### 第 16 条强阻断规则

```
16. reviewer 输出必须遵循 schemas/reviewer-output-schema.md；缺失必填章节、缺 evidence
    reference、未声明 forbidden-behavior self-check 时，dispatcher 不得接受该 review
    artifact 作为 fixed review point 通过依据，必须重新调度该 reviewer。
```

#### 回归保障

- schema 缺失：手工构造缺章节的 review markdown，dispatcher 必须返回阻断；
- reviewer-eval：6 条 ground-truth 全部命中 expected flag 集合的子集；
- 漂移监控：reviewer profile 改动时，eval 结果差异计入 PR review 关注点（不在 v4.2 范围内做 CI，但留 hook）。

### 工作项 3 — per-question baseline 与 per-question frontier

#### 为什么需要

v4.1 的 `claims/baseline-snapshot.md` 是**单一表**：

```markdown
| Metric | Value | Source artifact |
| WAPE   | 0.288 | ... |
| Q2 obj | 9,016,061 | ... |
| Q3 obj | 9,893,432 | ... |
```

但竞赛中常见三类失真：

- 不同问题的主指标语义不同，混在一张表里 reviewer 难以识别"per-question 单调改进"；
- improvement round 通常只针对一个问题做改动，但当前 baseline 比较是**全表对比**，Q3 微调即使 Q1 全无变化也要把 Q1 行重新填一次，制造无意义噪音；
- 多问联动下，Q3 改进可能反向影响 Q1（共享数据流、共享设备约束、共享场地分配），单一 baseline 不会让 reviewer 注意到"Q3 提升 Q1 退步"这种 Pareto 退化。

#### 新增 / 改动

```
claims/baseline-snapshot.md                                  改造为索引
claims/baseline-q1.md                                        新增（per-question）
claims/baseline-q2.md                                        新增
claims/baseline-q3.md                                        新增

improvements/improvement-frontier.md                          改造为索引
improvements/frontier-q1.md                                   新增（per-question 四象限）
improvements/frontier-q2.md                                   新增
improvements/frontier-q3.md                                   新增

references/baseline-snapshot-template.md                      升级为多表模板 + 索引模板
references/improvements-templates.md                          升级 frontier 多表模板
references/protocol-improvement-loop.md                       明确 round-N.md 必须声明
                                                              `Target question` 与跨问题影响
SKILL.md §强阻断规则                                          追加第 17 条
```

#### 第 17 条强阻断规则

```
17. improvement round 必须在 round-N.md 元数据声明 Target question；改动若影响非 target
    question 的主指标，必须在 Risk assessment 段写明并附 per-question baseline 对照，
    Skepticism reviewer 必须就此发表意见。缺声明或缺对照时阻断。
```

#### round-N.md 元数据新增字段

```markdown
## Round metadata
- Round number: N
- Target question: Q3                                         ← 新增
- Cross-question impact expected: Q1 (no change), Q2 (no change)   ← 新增
- ...
```

#### 回归保障

`regression/baseline-per-question/` 新增 3 条 fixture：

1. `target-question-missing.md` — round-N.md 没声明 target question，期望阻断；
2. `cross-question-regression-not-flagged.md` — Q3 改进同时让 Q1 baseline 退步，但 round-N.md 没在 Risk assessment 写明，期望阻断；
3. `per-question-frontier-not-updated.md` — round close 时只更新了全局 frontier 索引而没更新 per-question frontier，期望阻断。

### 工作项 4 — stage-level 时间预算与 burn-down

#### 为什么需要

竞赛硬截止是 v4 / v4.1 没显式建模的**最大隐变量**。当前流程：

- 每个 stage 是否有时间限制全靠用户自己心算；
- 接近截止时是否应该降低 target claim level / 触发 model simplification，没有信号；
- 复盘时也没有 "Stage X 实际花了多久 / 在哪一步卡住"的可审计数据。

参考你 memory 里"rules-first methodology + ~1 个月迭代到稳定"的诉求：时间预算是规则的一部分，应当被 dispatcher 校验，不应留在用户脑子里。

#### 新增 / 改动

```
time-budget.md                                                项目根新增审计文件
references/protocol-time-budget.md                            新增协议
references/stage-1-problem-understanding.md                   各 stage 合同追加
                                                              `Time budget` 子段
…（stage-2 到 stage-10 同样追加）
SKILL.md §强阻断规则                                          追加第 18 条
SKILL.md §命令表                                              新增 /math-modeling time
```

#### `time-budget.md` 模板

```markdown
# Time Budget

## Hard deadline
2026-XX-XX HH:MM (timezone)

## Total budget
72 hours (or whatever the contest allows)

## Stage allocation
| Stage | Planned (h) | Spent (h) | Remaining (h) | Status |
|---|---|---|---|---|
| 1 Problem Understanding | 4 | - | - | not_started |
| 2 Algorithm Selection   | 6 | - | - | not_started |
| 3 Innovation Design     | 4 | - | - | not_started |
| 4 Model Specification   | 8 | - | - | not_started |
| 5 Solution Implementation | 16 | - | - | not_started |
| 6 Independent Validation | 8 | - | - | not_started |
| 7 Sensitivity Analysis  | 6 | - | - | not_started |
| 8 Visualization         | 6 | - | - | not_started |
| 9 Figure Review         | 4 | - | - | not_started |
| 10 Paper Materials      | 10 | - | - | not_started |

## Burn-down log
| Timestamp | Stage | Event | Δh |
|---|---|---|---|
```

#### `/math-modeling time` 命令

```
/math-modeling time             输出当前 burn-down 摘要 + 剩余预算 + 风险等级
/math-modeling time start N     标记 stage N 开始
/math-modeling time stop N      标记 stage N 结束
```

#### 第 18 条强阻断规则

```
18. 项目根存在 time-budget.md 时，dispatcher 在每次 stage 切换、improvement round 启动、
    /math-modeling export 之前必须读取剩余预算；剩余预算低于阈值（默认 20% 总预算）时，
    必须 emit time-pressure advisory 并要求用户确认是否降低 target claim level、
    精简 stage 工作或触发 model simplification reviewer。沉默不等于确认。
```

#### 回归保障

`regression/time-budget/` 新增 4 条 fixture：

1. `stage-switch-without-time-update.md` — 切换 stage 但 `time-budget.md` 未更新 burn-down，期望阻断；
2. `improve-with-low-remaining-budget.md` — 剩余预算 <20% 仍调用 `/math-modeling improve`，期望前置 advisory + 要求用户确认；
3. `export-with-overrun.md` — 超过 hard deadline 调用 `/math-modeling export`，期望阻断；
4. `time-budget-absent-no-error.md` — 未配置 `time-budget.md` 的项目（保持可选），dispatcher 行为与 v4.1 完全一致。

### 工作项 5 — export-time paper grounding scanner

#### 为什么需要

v4 / v4.1 的 `claims/claim-registry.md` 是 claim 注册表，Stage 10 的 `reviews/stage10-evidence-claim-review.md` 是 reviewer 视角的人工审查。但是论文素材（数字、公式、图、表）真正进入论文 markdown / docx 时，是否每一项都能在 registry 找到 grounding，**仍然依赖 reviewer 的眼力**。这是 v4.1 没盖到的最后一道 hallucination 漏洞，也是真实比赛里数字写错的高发位置。

#### 新增 / 改动

```
references/protocol-paper-grounding-scan.md                   新增协议
regression/command_export_flow.py                             升级，挂入 grounding scan
regression/paper-grounding/                                   新增 fixture 目录
  ├── happy-path-all-grounded/
  ├── number-without-claim-entry/
  ├── figure-without-meta-json/
  └── formula-without-derivation-link/
SKILL.md §强阻断规则                                          追加第 19 条
```

#### 第 19 条强阻断规则

```
19. /math-modeling export 在 Final Evidence Gate 之前必须运行 paper-grounding scan：
    论文素材中每个数字、公式、图、表必须在 claims/claim-registry.md 找到对应 entry，
    每张图必须有同名 .meta.json，每个公式必须链接到 stage-4 模型规格或 stage-7 推导
    artifact。任一项缺失即阻断 export，不得仅作为 warning。
```

scanner 的实现以**纯 markdown 文本扫描 + 显式 anchor**为主，不做 LLM 语义匹配（避免引入新故障源）：

- 数字：约定论文 markdown 中所有 claim 数字使用 `<!-- claim: <claim-id> -->` HTML 注释 anchor；scan 时校验 claim-id 在 registry 存在；
- 图：扫描所有 `![](path/to/x.png)`，校验 `path/to/x.meta.json` 存在；
- 公式：约定使用 `<!-- derivation: <stage-4-section-id> -->` 或 `<!-- derivation: stage-7/<file>:<section> -->`，校验路径与锚点存在；
- 表：扫描表格上方的 `<!-- claim-table: <claim-id> -->` 注释，与数字同规则。

#### 回归保障

paper-grounding fixture 4 条全部期望对应阻断；happy-path 期望 export 完整通过且 Final Evidence Gate 看到 scanner 输出的 PASS 记录。

## 风险

### 风险 1：reviewer schema 过严导致 reviewer 输出反复被打回

第 16 条会让 reviewer 在缺 forbidden-behavior self-check 时被 dispatcher 拒绝。

缓解：schema 提供最小化模板（5 段必填 + 可选段），并在 `reviewer-output-schema.md` 顶部给一个 ready-to-paste 骨架；regression/reviewer-eval/ 提供"合法最小输出"基线 fixture，让 reviewer 有可参照样例。

### 风险 2：per-question baseline 制造维护噪音

3 个问题就要维护 3 张 baseline + 3 张 frontier，single-question 项目反而更繁琐。

缓解：模板支持单问降级写法（只写 `claims/baseline-q1.md` 不强制其它），索引文件 `baseline-snapshot.md` 自动列出已存在的 per-question 文件；只有 round-N.md 改动跨问题时才强制对照。

### 风险 3：time-budget 误触发 advisory 干扰主流程

阈值 20% 在 72h 比赛是 14.4h，仍有相当多工作要做；advisory 反复触发会让用户疲劳。

缓解：advisory 必须由用户 confirm 一次后，同 stage 内不再重复触发；用户可在 `time-budget.md` 元数据里覆盖默认阈值。

### 风险 4：paper-grounding scanner 误判格式化数字

论文中的"95% 置信区间""图 3"等表述若没有 anchor，会被误判为缺 grounding。

缓解：scanner 默认只校验**显式标注 claim 的数字**（带 `<!-- claim: ... -->` 注释或在表格里有 `claim-table` 注释），未标注的描述性数字不视为 claim；约定写在 `protocol-paper-grounding-scan.md` 顶部。Stage 10 reviewer 仍负责审查"应当被 anchor 但没 anchor"的情况，scanner 与 reviewer 互补不替代。

### 风险 5：v4.2 文件总量增加，可读性下降

新增协议、schema、4 类 fixture 目录，新人上手成本上升。

缓解：在 README.md 增加 "v4.2 hardening 概览"小节，给五个工作项一句话索引；DELIVERY.md 同步更新。
